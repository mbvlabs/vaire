## P1 — doctor activity-health reads can hold node locks indefinitely

**Status:** fixed and committed; not live-qualified, so it stays open until qualified. An independent reviewer rated the original defect P2; the parent review rated it P1 because of its effect on locked operations.

**Where and how the defect occurred:**

- `internal/node/doctor.go`, `gatherActivityHealth` / `activityStoreHealth`, created a three-second context but called `Store.Health` synchronously.
- `internal/activity/health.go`, `Store.Health`, performs filesystem operations such as `Lstat`, state reads, segment listing and retained-bound reads. Context cancellation cannot interrupt an already-stalled filesystem call.
- `internal/node/jobs.go`, the `quietJobs` branch in `RunJob`, acquires a shared node lock for the doctor timer before calling `runQuietJob`.
- `internal/node/methods.go`, `handleApply`, invokes `doctorGate` at the end of a full apply; a node-wide apply holds the exclusive node lock through the handler. Other operations requiring a conflicting lock could consequently be blocked or refused while the health read remained stuck.

**Evidence and limits:** a temporary hook-driven unit test held a read inside `Health` past its context deadline. The call stayed blocked until the hook was released, confirming the defect. That test was removed after the review. This simulates a stalled read; no actual filesystem hang was induced and no live server was tested. A filesystem-wide stall might also block other operations, but the problematic path is reachable when the activity-store read stalls while the rest of the operation could otherwise proceed.

**Fix:** in `internal/node/doctor.go`, `activityStoreHealth` now runs `Store.Health` on one background goroutine and the doctor caller waits for it at most `activityHealthWait` (three seconds, the same budget the read's own context gets). A wait that expires, a store error and a panicking store all leave the activity facts unknown; unknown is never rendered as healthy, because `activityStorage` warns and `activityPermissions`/`activityCoverage` skip. A typed `Health` reading, including loss, permissions and budget failures, still arrives with `known` true so real health failures stay visible. `gatherActivityHealth` opens the store through the existing `activityStoreFactory` seam, which is also how the tests inject a stalled store.

At most one health read may be in flight per process (`activityHealthInFlight`). A store call that ignores cancellation pins that goroutine for as long as the filesystem stalls it; while it is stuck, later doctor runs report the history as unknown at once instead of starting another goroutine. The bounded caller wait and the bounded background work are therefore separate guarantees.

The node lock needs no healing: `RunJob`'s quiet-job branch and the apply dispatcher already release it with `defer`, so the lock is released as soon as the doctor caller returns, while the abandoned read may still be stuck. No repair or retry was added.

**Regression coverage:** `internal/node/activity_health_test.go` holds a deterministic hook-driven stalled store (it ignores its context) and shortens the wait. `TestActivityHealthStallIsBounded` proves the doctor caller returns unknown within the bound while the store is still blocked, and that the next run reads real health once the store answers. `TestActivityHealthKeepsOneReadInFlight` proves fifty further stalled runs return unknown at once, reach the store only once and add no unbounded goroutines, then recover. `TestActivityHealthStallReleasesTheNodeLock` models the shared and exclusive node lock with a real flock around the caller's deferred release and proves the lock is free while the read is still blocked. `TestActivityHealthFailureIsUnknown`, `TestActivityHealthPanicIsUnknown` and `TestActivityHealthKeepsTypedFailureVisible` preserve real failures: a failed or panicking read is unknown, never healthy, while typed loss and permissions data still reaches the checks. The existing `TestActivityHealthDoesNotCreateStore`, `TestActivityHealthNilStore`, `TestActivityHealthCanceledContext` and `TestActivityHealthUnsafeDirectory` remain. Fix verified with `go build ./...`, `go vet ./...`, `go test ./...`, `golangci-lint run ./...`, `GOOS=darwin GOARCH=arm64 go build ./...` and `just lint`, all passing.

## P2 — retention rotation can falsely report evidence loss

**Status:** fixed and committed; not live-qualified, so it stays open until qualified.

**Where and how:** `internal/activity/query.go` and `internal/activity/health.go` read the store state, list segments, calculate retained bounds and infer missing evidence when the observed last sequence is behind the state. During normal retention rotation, a listed segment can disappear before its bounds are read, while the newly created segment may not yet be represented as a complete event in the reader's snapshot. The mixed snapshot can look like lost evidence even though retention behaved normally. `readRetainedBounds` is in `internal/activity/query.go`; rotation and pruning are in `internal/activity/store.go`.

**Impact:** `Query` can return no events and set `LossDetected` and `Partial`; `Health` can set `LossDetected`, leading doctor or incident diagnostics to report loss on a healthy store. This is transient, not proof that events were damaged. It can occur under time-based or byte-budget pruning.

**Evidence and limits:** a temporary test triggered a retention rotation after the reader listed segments. Both query and health reported loss; a fresh health read immediately afterward was clean. The temporary test was removed. Existing `TestConcurrentReadsNeverInventLoss` in `internal/activity/race_regressions_test.go` explicitly runs without retention and does not cover this case.

**Fix:** `internal/activity/query.go` now has `observeStore` and `observeStoreOnce`: the state read, segment listing, first-append recheck and retained-bound read form one observation, and `readRetainedBounds` reports when a listed segment vanished before its edge could be read. On a vanish the whole observation restarts from state, not just the listing: re-listing alone would pair a stale state with a newer history, exactly the mixed snapshot the loss check must not trust. The restart is bounded by `maxSnapshotAttempts` (four attempts). A normal rotation invalidates only the attempt it raced, so the next state-then-listing observation is consistent. `Query` and `Health` infer missing evidence only from an observation whose bound read did not lose a listed segment. If every attempt still races rotation, the read does not turn the remaining inconsistency into loss: `Query` reports `Truncated` and `Partial` instead of a false loss verdict, and `Health` keeps `LossDetected` to its concrete counters. Genuine loss remains visible because the retry re-reads state and the listing together: an externally deleted successor segment leaves a consistent observation in which the state's last sequence is still ahead of the retained last event, so both readers report loss. Retention policy, the recorded event set and the lock protocol are unchanged.

**Regression coverage:** `internal/activity/retention_race_test.go` adds deterministic hook-driven tests. `TestRetentionRotationDoesNotReportLoss` rotates and prunes through `afterListSegmentsHook` between listing and bound reads, for both `Query` and `Health`, under time-based and byte-budget pruning, with one race and with three successive races; it asserts no loss, all injected rotations reached the read, and the final snapshot is complete with the single retained segment and event. `TestRetentionRaceRetryIsBounded` races a rotation against all four attempts and asserts the read terminates with an incomplete snapshot rather than loss. `TestRetentionRetryStillReportsMissingNewestSegment` deletes the newest segment between listing and bounds, confirms a fresh observation happened, and requires both readers to report the resulting genuine loss, so the retry cannot hide it. Existing `TestConcurrentReadsNeverInventLoss` is unchanged, and the existing missing-history and torn-tail tests still pass. Negative control: temporarily restoring the pre-fix `query.go`, `health.go` and `segment.go` made all three new tests fail (query and health reported loss, or the retry never happened); restoring the fix passed. `go build ./...`, `go vet ./...`, `go test -count=1 ./...`, `golangci-lint run ./...`, `GOOS=darwin GOARCH=arm64 go build ./...` and `just lint` pass with the fix.

## P2 — duplicate warning events print twice in human output

**Status:** fixed and committed; not live-qualified, so it stays open until qualified.

**Where and how:** an activity write failure can emit an `activity_not_recorded` warning as it happens (`recordStep` in `internal/node/activity.go`). On a successful RPC, `finishActivitySuccess` adds the warning to the result and `eventWriter.ok` in `internal/node/dispatch.go` emits it again. A successful job follower can similarly replay a journal warning and return it in its result. `progress.event` and `progress.liveEvent` in `internal/cli/progress.go` render each warning event without checking whether it was already printed. Structured final warning lists are deduplicated.

**Evidence and limits:** `TestProgressPreservesEvidenceWarningsInResult` in `internal/cli/progress_warnings_test.go` already sends the same event twice in human mode, but checks only that the warning appears, not its count. The duplicate follows from those event and rendering paths; the review did not run a live node test.

**Fix:** the human renderer now owns the "already printed" check in `internal/cli/progress.go`. `progress` records each warning it prints in `warned`, keyed by the redacted code and message that identify a notice in the structured result. `progress.event` claims a warning before dispatching it to either the plain warning line or `liveEvent`; a later event with the same key returns without printing. This covers both duplicate sources: the live warning plus the same result warning that `eventWriter.ok` emits, and a job follower's replayed journal warning plus the warning in its result. A distinct warning with the same message but another code still prints, because the key includes both fields. Nothing changes on the node or on the wire: JSON, agent and stream envelopes keep their existing warning lists and warning events, and a result warning that was not streamed still reaches the human once from the result. The check sits after the stream and structured early returns and after the hidden-code check, so stream, JSON, agent, jq, markdown and quiet output are untouched. Failure output uses the same path: `unshownWarnings` still leaves out a result warning already printed, while duplicate warning events now print once.

**Regression coverage:** `TestProgressPreservesEvidenceWarningsInResult` now asserts the human output contains the warning exactly once, in addition to the existing JSON and agent envelope-count checks. `TestProgressHumanPrintsEachWarningOnce` feeds duplicate and distinct warnings to both plain and rich output and asserts each distinct warning appears once. `TestProgressHumanKeepsDistinctWarningIdentities` proves the key is the warning identity, not one visible field: warnings with the same message but different codes, and warnings with the same code but different messages, both stay distinct. `TestProgressHumanPrintsReplayedResultWarningOnce` models a follower: a duplicated journal warning plus the same warning in an explicit result prints once and is not repeated by the result. `TestProgressStreamKeepsWarningEventsAndOneResultWarning` and `TestProgressQuietHumanKeepsWarningsOut` keep the unchanged stream and quiet contracts. `TestFailureHumanPrintsEachWarningOnce` now repeats the warning event and still requires one visible warning. Negative control: removing the `claimWarning` gate made the new human-count assertions fail with two or three printed copies in plain and rich mode; restoring it passed. `go build ./...`, `go vet ./...`, `go test -count=1 ./...`, `golangci-lint run ./...`, `GOOS=darwin GOARCH=arm64 go build ./...` and `just lint` pass with the fix.

## Additional questions and limitations: decided 2026-10-28

These were noted during review without an established release-blocking defect. The operator decided them on 2026-10-28; none blocks the release:

- **Terminated job:** no code change. The synthesized failure is enough; [ACTIVITY.md](ACTIVITY.md) now states that such a job never has a final activity event and gets no separate evidence warning.
- **RPC failure envelope:** no code change. The event stream is the contract; [ACTIVITY.md](ACTIVITY.md) now states that a raw `vaire node rpc` consumer must read streamed warnings.
- **Settlement state lock:** no code change. A stall on `state.json` breaks every vaire operation anyway, and abandoning a save midway risks a torn state file. Recorded here as a known limitation.
- **Retention capacity:** no change now; watch it. Every recorded node call counts, including successful reads, and `status --watch` refreshes every 5 seconds, so a long-running watcher could fill the 32 MiB store in days and prune older mutation history early. Revisit, for example by not recording successful read-only calls, if live use shows history ending well short of 14 days.

The original review notes follow.

- **Abruptly terminated job and evidence warning.** If a unit ends before it records a terminal job result, `internal/node/jobs.go` synthesizes a failed result with `ended without recording a result`. In that path `ActivityPending` may never have been set, so the follower does not necessarily add a separate `activity_not_recorded` warning. A reviewer rated this P2; assess whether the existing failure plus the documented meaning of a missing final activity event is sufficient, or whether the follower contract requires an explicit evidence warning. Do not claim the completion event exists when its presence is unknown.
- **Raw node-RPC failure envelope.** For an ordinary failing node method, the evidence warning may be sent as a streamed warning event but not included in the terminal failure envelope (`internal/node/dispatch.go`). CLI call paths reviewed collect warning events and carry them into their output; a raw RPC consumer must inspect the stream. Assess whether the RPC contract requires the terminal envelope to carry it too. The reviewer described this as a boundary limitation, not an established regression.
- **Job evidence settlement after lock acquisition.** `internal/node/activityjob.go` bounds the job's wait to two seconds and caps concurrent settlement goroutines; `internal/engine/state.go` bounds waiting for the state lock. Once acquired, state load and save are synchronous and not cancellable. A stalled settlement can therefore retain the state lock until I/O finishes or its process exits, potentially affecting other state writers even after the original job stops waiting. The exact operational impact of a real stall was not reproduced; assess it separately from the confirmed doctor blocker.
- **Retention capacity.** The byte limit can be reached before the nominal retention duration under sufficiently frequent reads such as `status --watch`. This is a bounded-storage policy observation, not the false-loss race above; impact was not measured. Changing which events are recorded or the retention policy requires a separate product decision.
